# LLM 推理优化的主要手段有哪些？

> 分类：模型推理与微调 ｜ 难度：★★★（高频）

## 一句话结论

先分瓶颈再谈手段：decode（逐 token 生成）是显存带宽瓶颈，主手段是批处理、量化、KV Cache 压缩；prefill（处理输入 prompt）是算力瓶颈，主手段是 prefix caching 和 PD 分离。默认答案：用 vLLM/SGLang 这类推理框架（内置 continuous batching + PagedAttention）+ GQA 模型，是否叠加量化用评测数据决定。

## 机制原理

**1. 两个阶段、两种瓶颈，是所有手段的索引。**

- prefill：输入的所有 token 已知，拼成大矩阵并行算，吃算力（compute-bound），决定首 token 延迟 TTFT。7B 模型 8K 输入的 prefill ≈ 2×7×10⁹×8×10³ ≈ 1.1×10¹⁴ FLOPs，H800 上百毫秒量级（量级估计，MFU 50%）。
- decode：每步只有 1 个新 token，小矩阵乘，算力用不满，成本全在「把 14GB 权重从显存读一遍」上（memory-bound），决定每 token 延迟 TPOT。batch=1 时算力利用率不到 1%，推导见 [KVCache为什么省算力](KVCache为什么省算力.md)。

**2. decode 侧手段：让每次权重读取产出更多 token。**

批处理是第一杠杆：batch=N 时权重读一次产出 N 个 token，等效带宽利用率近似 ×N。静态 batching 的缺陷是最长请求拖住整批（队头阻塞），continuous batching 按迭代级调度、请求完成即退出、新请求即补入，已成 vLLM 等框架标配：

| | 静态 batching | continuous batching |
| --- | --- | --- |
| 批的进出 | 整批一起进、一起出 | 迭代级调度，请求级进出 |
| 队头阻塞 | 短请求干等最长的 | 完成即释放 |
| GPU 空转 | 常见 | 几乎没有 |
| 典型实现 | 自研简单框架 | vLLM / SGLang / TGI |
| 代价 | 实现简单 | 需要调度器与抢占管理 |

量化是第二杠杆：decode 的读取量正比于权重字节宽，fp16→int4 权重 14GB→3.5GB，decode 吞吐理论上限 ×4（量级估计，忽略 KV 读取与反量化开销），腾出的显存还能装更大 batch。代价是精度损失，必须过评测回归。注意量化主要提速 decode，对 compute-bound 的 prefill 帮助有限。

KV Cache 压缩是第三杠杆：GQA/MQA 降 KV 头数、KV 量化降位宽、PagedAttention 把 KV 按分页管理（vLLM 论文实测传统实现 KV 显存浪费普遍超六成，分页后压到 4% 以内），显存利用率上来后并发容量翻倍是常见量级（量级估计）。

**3. prefill 侧与跨阶段手段。**

- prefix caching：相同前缀（system prompt、few-shot、文档块）的 KV 只算一次、全局复用，命中时 TTFT 大幅下降；对固定开场白占比高的业务近乎白捡。
- PD 分离：prefill 吃算力、decode 吃带宽，混部时长 prompt 的 prefill 会卡住同实例所有请求的 decode；把两个阶段拆到不同卡上部署，各自调度扩缩。代价是 KV cache 要跨卡传输，适合长输入流量占比高的服务。
- 投机解码：小模型先起草多个 token，大模型一次前向并行验证，接受/拒绝采样保证输出分布不变——本质是把「大模型每步只产 1 token」的带宽浪费摊薄，典型加速 2~3 倍（经验判断）。

**4. 汇总一张表，先测量再选手段。**

| 手段 | 作用阶段 | 机制 | 收益量级 | 代价 |
| --- | --- | --- | --- | --- |
| continuous batching | decode | 多请求分摊权重读取 | 吞吐 ×几~几十（量级估计） | P99 延迟上升 |
| 量化 int8/int4 | decode | 位宽↓→权重读取量↓ | 吞吐 ×2~4，显存 ÷2~4（量级估计） | 精度需评测 |
| GQA / KV 量化 | decode + 显存 | KV 体积↓ | 并发容量 ×数倍（量级估计） | 轻微精度损失 |
| PagedAttention | 显存利用率 | 分页消除碎片 | 并发 ×2~4（量级估计） | 无明显 |
| prefix caching | prefill | 前缀 KV 复用 | TTFT 视命中率而定 | 管理复杂度 |
| PD 分离 | 全链路 | 两阶段拆开各治各的瓶颈 | 长输入场景 P99 明显改善 | KV 跨卡传输开销 |
| 投机解码 | decode | 草稿 + 并行验证 | 延迟 ×2~3（经验判断） | 需草稿模型 |

数字只是量级锚点。动手前先在监控里找到对应瓶颈（TTFT 高还是 TPOT 高、显存还是带宽打满），再选手段；批大小与吞吐/延迟的平衡怎么算账，见场景题 [LLM 推理服务平台](../../system-design/questions/ai/LLM推理服务平台.md)。

## 典型错误答案

1. 「batch 越大吞吐一定越高，直接把 batch 拉满。」
   ——batch 增大后先撞显存：每条请求的 KV Cache 都要常驻，batch × 上下文长 × 0.5MB/token 的量级很快吃满 80GB；即使装得下，注意力要读的 KV 总量也随 batch 线性涨，单请求 TPOT 变慢、P99 恶化。吞吐和延迟之间是平衡关系，不是单调关系。

2. 「量化就是无脑砍到 int4，效果差不多。」
   ——量化误差对权重中的异常值敏感，小模型冗余更少，是否可接受取决于任务，必须用困惑度 + 下游任务回归验证。另外 int4 主要省 decode 的权重读取，长 prompt 的 TTFT 是算力瓶颈，几乎没收益。

3. 「推理太慢？用 LoRA 微调一下模型就快了。」
   ——微调改变的是模型行为（输出分布、任务适配），不改变 decode 每步读权重的带宽瓶颈，模型该多慢还是多慢。提速要么在系统层（批处理/量化/调度），要么换更小的模型。微调解决「答得好不好」，推理优化解决「跑得快不快」，是两条不相干的轴。

## 追问

1. **TTFT 和 TPOT 分别怎么优化？**
   - 思路：先定位哪个指标差。TTFT 高 → prefill 问题 → prefix caching、PD 分离、缩短输入；TPOT 高 → decode 问题 → 批处理、量化、GQA。两种瓶颈机制不同、手段不通用，别拿量化去治 prefill。
   - 可补一句：PD 分离之所以存在，就是把这两组手段放到不同实例上各自放大，互不拖累。

2. **continuous batching 比静态 batching 好在哪，为什么成了标配？**
   - 思路：抓「进出单位」这一个词——静态按批进出、最长请求决定整批寿命；continuous 按请求进出、消除队头阻塞。再补一句代价（需要调度器与抢占管理），显得懂工程取舍。
   - 若追问「什么场景静态也够」：离线批量任务（调用方不等结果）用静态问题不大，在线服务几乎必须 continuous。

3. **投机解码为什么不会改变模型输出？**
   - 思路：关键在验证步——大模型对草稿 token 做一次并行前向打分，用接受/拒绝采样校正，数学上保证最终分布与逐 token 自回归一致。加速的本质是大模型一次 forward 验证多个 token，摊薄了带宽成本。

4. **什么时候值得自部署做这些优化，什么时候直接调 API？**
   - 思路：给经验判断——量大到 API 账单显著高于自部署、有数据合规或内网要求、需要深度定制时才值得自部署；否则优化做得再好也难打平 API 的规模摊薄。成本账怎么算见场景题 [Token 成本治理](../../system-design/questions/ai/Token成本治理.md)。
   - 若追问「调 API 是不是就不需要懂这些」：不是——批处理、量化、投机解码是模型供应商的供给侧优化，直接体现在 API 的价格和速度上，理解机制才看得懂报价差异和选型理由。
